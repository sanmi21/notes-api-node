# Scale 1 Authentication Implementation Guide

## Purpose of this document

This document explains the Scale 1 authentication code that has been added to the Notes API.

It covers:

- What files were created or changed.
- What every new function does.
- What information is stored in the database.
- How each authentication route works.
- How signup, login, password reset, and MFA work from beginning to end.
- What security protections are already present.
- What is deliberately left for later phases.

For instructions on sending the requests yourself, use the [Scale 1 Testing Guide](./scale-one-testing.md).

## What was implemented

Scale 1 now includes these complete user journeys:

1. A user creates an account with an email and password.
2. The password is hashed before it is saved.
3. The user logs in and receives a short-lived access token.
4. The access token opens protected API routes.
5. The user can request and complete a password reset.
6. The user can connect an authenticator app.
7. Once MFA is enabled, the password and authenticator code are both required during login.
8. The user can disable MFA using both the password and a current authenticator code.

## Important terms

| Term | Meaning in this project |
|---|---|
| Authentication | Proving who is making the request. |
| Authorization | Deciding what an authenticated user is allowed to access. |
| Password hash | A one-way protected version of a password stored in the database. |
| Access token | A temporary JWT that allows a client to call protected API routes. |
| MFA | Multi-factor authentication: requiring both a password and an authenticator code. |
| TOTP | The time-based six-digit code generated by an authenticator app. |
| MFA challenge token | A temporary token proving the password was correct but MFA is not finished yet. |
| Password-reset token | A random, short-lived, single-use secret that allows a password to be replaced. |
| Token hash | A protected representation of a token stored instead of the original token. |

## Database changes

The `User` database model now contains:

| Field | What it stores | Why it exists |
|---|---|---|
| `id` | The user's numeric ID. | Provides a stable identity for tokens, notes, and lookups. |
| `email` | The normalized email address. | Used as the login name and must be unique. |
| `password` | The bcrypt password hash. | Lets the API verify a password without storing the original password. |
| `mfaEnabled` | `true` or `false`. | Tells login whether an authenticator code is required. |
| `mfaSecret` | The secret shared with the authenticator app. | Allows the server to verify time-based codes. |
| `passwordResetTokenHash` | A SHA-256 hash of the current reset token. | Prevents the original reset token from being stored in the database. |
| `passwordResetExpiresAt` | The time the reset token stops working. | Limits how long a stolen reset token can be used. |
| `notes` | The user's related notes. | Existing ownership relationship. |

An index was added to `passwordResetTokenHash`. The index helps the database find the owner of a submitted reset token quickly.

## Configuration values

The authentication code understands these environment variables:

| Variable | Purpose | Default |
|---|---|---|
| `JWT_SECRET` | Secret used to sign and verify JWTs. | Required; the server refuses to start without it. |
| `JWT_ISSUER` | Name of the system that issued the token. | `notes-api` |
| `JWT_AUDIENCE` | Name of the API allowed to accept the token. | `notes-api` |
| `JWT_ACCESS_EXPIRES_IN` | Access-token lifetime. | `30m` |
| `MFA_CHALLENGE_EXPIRES_IN` | MFA challenge lifetime. | `5m` |
| `AUTH_EXPOSE_TEST_TOKENS` | Returns reset tokens in local responses for manual testing. | `false` |
| `PASSWORD_RESET_URL` | Frontend address used to build a password-reset link. | `http://localhost:3000/reset-password` |
| `SMTP_HOST` | Address of the email server. | No default |
| `SMTP_PORT` | Port used by the email server. | `587` |
| `SMTP_USER` | SMTP username. | No default |
| `SMTP_PASS` | SMTP password. | No default |
| `EMAIL_FROM` | Sender displayed in reset emails. | `Notes API <no-reply@example.com>` |

`AUTH_EXPOSE_TEST_TOKENS=true` is only a testing convenience. The code refuses to expose reset tokens when `NODE_ENV=production`.

## Token service

The token service is located in `src/auth/tokens.js`.

### `commonOptions(expiresIn)`

This private helper builds the settings shared by both JWT types.

It sets:

- Signing algorithm: `HS256`.
- Token issuer.
- Token audience.
- Token lifetime.

Using one helper keeps the creation rules consistent.

### `createAccessToken(userId)`

This creates the normal token used for protected API requests.

Its important contents are:

```json
{
  "sub": "123",
  "token_use": "access",
  "iss": "notes-api",
  "aud": "notes-api",
  "iat": 1234567890,
  "exp": 1234569690
}
```

- `sub` means subject. It identifies the user.
- `token_use` says this is an access token.
- `iss` identifies who created it.
- `aud` identifies which API may accept it.
- `iat` records when it was created.
- `exp` records when it expires.

The user ID is converted to a string before being stored as `sub`, following normal JWT claim conventions.

### `createMfaChallengeToken(userId)`

This creates a five-minute token after the password is correct but MFA still needs to be completed.

It looks similar to an access token, but it contains:

```json
{
  "token_use": "mfa"
}
```

That difference is essential. The MFA challenge proves only that the password step succeeded. It cannot be used as the final login credential.

### `verifyToken(token, expectedUse)`

This verifies a JWT before the API trusts it.

It checks:

1. The token signature is valid.
2. The token uses the expected `HS256` algorithm.
3. The issuer matches this API.
4. The audience matches this API.
5. The token has not expired.
6. The token has the expected purpose, such as `access` or `mfa`.
7. The subject contains a valid positive user ID.

The function then returns the verified token information plus a numeric `userId` used by the existing route code.

## Access-token middleware

The `authenticateToken` function is in `src/middleware.js`.

It protects routes such as `/auth/me`, MFA setup, and all note routes.

The process is:

```text
Request arrives
    ↓
Read the Authorization header
    ↓
Require exactly: Bearer <token>
    ↓
Verify that it is a valid access token
    ↓
Attach the verified user information to req.user
    ↓
Allow the protected route to continue
```

If the token is missing, malformed, expired, signed incorrectly, or is actually an MFA challenge token, the middleware returns `401`.

The existing `verifyNoteOwnership` middleware remains responsible for ensuring the authenticated user owns the requested note. Authentication proves identity; ownership checking protects another user's data.

## Password-reset helpers

The password-reset helpers are in `src/auth/password-reset.js`.

### `createPasswordResetToken()`

This function creates 32 cryptographically random bytes and encodes them into a URL-safe string.

It returns three values:

- `token`: the original secret sent to the user.
- `tokenHash`: the SHA-256 hash saved in the database.
- `expiresAt`: 15 minutes after creation.

The original token and its hash serve different purposes:

```text
Original token → sent to the user
Hash           → stored in the database
```

If the database is leaked, the stored hash is not the same value needed to reset the password.

### `hashPasswordResetToken(token)`

This converts a submitted reset token into its SHA-256 hash.

The API looks for that hash in the database instead of looking for the original token.

## Email service

The email service is located in `src/services/email.service.js`.

### `getTransporter()`

This private helper prepares Nodemailer using the configured SMTP server.

- If SMTP has already been prepared, it reuses the same transporter.
- If `SMTP_HOST` is missing, it returns `null`.
- Port `465` uses a secure SMTP connection immediately.
- Other ports, such as `587`, begin with the normal SMTP upgrade process.

### `sendPasswordResetEmail({to, token})`

This builds a reset address containing the original reset token.

Its behavior depends on the environment:

| Environment | Behavior |
|---|---|
| Local development without SMTP | Prints the reset link in the server terminal. |
| Automated test | Performs no external email operation and prints no token. |
| Configured SMTP environment | Sends a text and HTML email through Nodemailer. |
| Production without SMTP | Throws an error because silently pretending to send an email would be misleading. |

## Route helpers

The following private helpers live in `src/routes/auth.js`.

### `normalizeEmail(value)`

This accepts an email input, removes surrounding spaces, and converts it to lowercase.

Example:

```text
"  Mentor@Example.com " → "mentor@example.com"
```

Signup, login, and password reset all apply the same normalization rule.

### `isValidEmail(email)`

This performs a basic email-shape check and rejects addresses longer than 254 characters.

It is deliberately a simple validation rule. Email ownership will be proven later through email verification rather than by attempting to create an overly strict regular expression.

### `validatePassword(password)`

This ensures the password:

- Is a string.
- Contains at least 8 characters.
- Contains no more than 128 characters.

It returns an error message when validation fails and `null` when the password is acceptable.

The minimum will become stronger in the later hardened-password phase. Eight characters is the current Scale 1 learning baseline.

### `accessTokenResponse(userId)`

This creates the standard successful token response:

```json
{
  "access_token": "<signed JWT>",
  "token_type": "Bearer",
  "expires_in": 1800
}
```

`1800` seconds equals 30 minutes.

## Route-by-route explanation

## `POST /auth/signup`

### Purpose

Create a new user account.

### Request

```json
{
  "email": "mentor@example.com",
  "password": "correct-password"
}
```

### Workflow

```text
Receive email and password
    ↓
Normalize and validate the email
    ↓
Validate password length
    ↓
Check whether the email already exists
    ↓
Hash the password with bcrypt using cost 10
    ↓
Save the user
    ↓
Return only the user ID and email
```

### Main responses

- `201`: Account created.
- `400`: Email or password does not meet the current rules.
- `409`: Email is already registered.
- `500`: Unexpected server or database failure.

The password and password hash are never returned.

## `POST /auth/login`

### Purpose

Check the user's email and password and decide whether login is complete or requires MFA.

### Workflow without MFA

```text
Normalize email
    ↓
Find the user
    ↓
Compare submitted password with bcrypt hash
    ↓
MFA is disabled
    ↓
Issue the access token
```

### Workflow with MFA

```text
Normalize email
    ↓
Find the user
    ↓
Compare submitted password with bcrypt hash
    ↓
MFA is enabled
    ↓
Issue a five-minute MFA challenge token
    ↓
Do not issue an access token yet
```

An unknown email and an incorrect password both return `Invalid credentials`. This avoids directly telling a caller whether an account exists.

## `GET /auth/me`

### Purpose

Provide a small protected endpoint that proves the access token works.

The access-token middleware runs first. The route then loads the current user and returns:

```json
{
  "id": 1,
  "email": "mentor@example.com",
  "mfa_enabled": false
}
```

If the user was deleted after the token was issued, the route returns `401`.

## `POST /auth/forgot-password`

### Purpose

Begin password recovery without revealing whether the submitted email is registered.

### Workflow

```text
Normalize submitted email
    ↓
If it belongs to a user, generate a reset token
    ↓
Store only its hash and expiration time
    ↓
Deliver the original token through the email service
    ↓
Return the same general message for existing and unknown emails
```

The normal response is:

```json
{
  "message": "If that email is registered, a password reset message has been prepared."
}
```

When local test-token exposure is enabled, the response also contains `reset_token`. This is for Thunder Client testing only.

Requesting another reset replaces the earlier reset token, so only the newest one remains valid.

## `POST /auth/reset-password`

### Purpose

Replace the password using a valid reset token.

### Request

```json
{
  "token": "<reset token>",
  "password": "new-correct-password"
}
```

### Workflow

```text
Validate the token and new password inputs
    ↓
Hash the submitted reset token
    ↓
Find a user with the same hash and an unexpired token
    ↓
Hash the new password with bcrypt
    ↓
Update the password only if the token is still valid
    ↓
Clear the reset-token hash and expiration
```

The conditional database update is important. Once one request clears the token, another request cannot use the same token successfully.

## `POST /auth/mfa/setup`

### Purpose

Start connecting an authenticator app.

### Authentication

Requires a valid access token.

### Workflow

```text
Verify the access token
    ↓
Load the current user
    ↓
Refuse if MFA is already enabled
    ↓
Generate a random TOTP secret
    ↓
Create a standard otpauth URI
    ↓
Save the secret but keep mfaEnabled = false
    ↓
Return the secret and URI
```

Saving the secret without immediately enabling MFA prevents the user from being locked out if the authenticator was not configured correctly.

## `POST /auth/mfa/enable`

### Purpose

Confirm that the authenticator app was configured correctly and then enable MFA.

### Authentication

Requires a valid access token.

### Request

```json
{
  "code": "123456"
}
```

### Workflow

```text
Require a six-digit code
    ↓
Load the saved MFA secret
    ↓
Verify the current time-based code
    ↓
Allow a small 30-second clock difference
    ↓
Set mfaEnabled = true
```

If the code is incorrect, MFA remains disabled.

## `POST /auth/mfa/verify`

### Purpose

Finish a login after the password step has succeeded for an MFA-enabled user.

### Request

```json
{
  "mfa_token": "<five-minute MFA challenge token>",
  "code": "123456"
}
```

### Workflow

```text
Validate the request shape
    ↓
Verify the MFA challenge signature, issuer, audience, expiry, and purpose
    ↓
Load the user and MFA secret
    ↓
Verify the authenticator code
    ↓
Issue the normal access token
```

This is the only point where an MFA-enabled password login becomes a fully authenticated session.

## `POST /auth/mfa/disable`

### Purpose

Turn off MFA without allowing someone holding only a stolen access token to do it easily.

### Authentication

Requires a valid access token.

### Request

```json
{
  "password": "new-correct-password",
  "code": "123456"
}
```

### Workflow

```text
Verify the access token
    ↓
Require both password and six-digit code
    ↓
Check the password and authenticator code
    ↓
Set mfaEnabled = false
    ↓
Delete the saved MFA secret
```

Both checks must succeed.

## Complete user workflows

## Signup and ordinary login

```text
POST /auth/signup
    ↓
Email normalized + password validated
    ↓
Password hashed and user stored
    ↓
POST /auth/login
    ↓
Password verified
    ↓
Access token returned
    ↓
GET /auth/me with Bearer token
```

## Password recovery

```text
POST /auth/forgot-password
    ↓
Random token created
    ↓
Token hash stored for 15 minutes
    ↓
Original token delivered to user
    ↓
POST /auth/reset-password
    ↓
Submitted token hashed and matched
    ↓
New password hashed and saved
    ↓
Reset token deleted
    ↓
User logs in with new password
```

## MFA enrollment

```text
Authenticated user calls POST /auth/mfa/setup
    ↓
API creates secret + otpauth URI
    ↓
User adds secret to authenticator app
    ↓
User sends current code to POST /auth/mfa/enable
    ↓
API verifies code
    ↓
MFA becomes active
```

## Login after MFA is enabled

```text
POST /auth/login with email + password
    ↓
Password succeeds
    ↓
API returns MFA challenge, not access token
    ↓
POST /auth/mfa/verify with challenge + current code
    ↓
Authenticator code succeeds
    ↓
API returns access token
    ↓
Client can call protected routes
```

## Application startup change

Previously, `src/app.js` both created the Express application and immediately opened a network port.

It is now split into two responsibilities:

- `src/app.js` builds and exports the application.
- `src/server.js` imports the application and starts listening.

This matters because automated tests can start the same application on a temporary port, send real HTTP requests to it, and close it afterward.

The application also limits JSON request bodies to `100kb`. Authentication requests need only small JSON bodies, so oversized input is rejected early.

## Automated test workflow

`test/auth.test.js` creates a temporary SQLite database and starts the real Express application on a temporary port.

The test proves:

1. Email normalization works.
2. The saved password is a bcrypt hash, not plaintext.
3. Incorrect passwords are rejected.
4. Login returns an access token.
5. Protected access fails without a token.
6. Protected access works with a valid access token.
7. Password reset issues a test token.
8. The password can be changed.
9. A reset token cannot be reused.
10. The old password stops working.
11. MFA setup returns a secret and standard URI.
12. MFA can be enabled with a valid generated code.
13. Password login returns only an MFA challenge afterward.
14. The MFA challenge cannot open a protected route.
15. An incorrect authenticator code is rejected.
16. A correct code returns an access token.
17. MFA can be disabled using the password and authenticator code.

The temporary database is deleted when the test finishes.

## Current security boundaries

This is a complete Scale 1 implementation, but it is not the final production system.

The following work remains intentionally scheduled for later phases:

- Login and MFA rate limiting.
- Email ownership verification.
- Refresh tokens.
- Device/session records.
- Logout and logout-all revocation.
- Revoking existing access tokens after password reset.
- Encrypting MFA secrets at rest.
- MFA recovery codes.
- Protection against reuse of the same TOTP code within its time window.
- Stronger production password rules and breached-password checking.
- Security-event logging and monitoring.
- Third-party OAuth and permission scopes.
- Browser-cookie and CSRF design.

Because access tokens are currently self-contained JWTs, changing the password does not immediately cancel an already-issued access token. It remains usable until its 30-minute expiration. Session-based revocation will solve this in the refresh-token phase.

## What “done” means for Scale 1

Scale 1 is considered functionally complete because:

- Every planned route exists.
- The normal user journeys work through HTTP.
- Passwords are not stored in plaintext.
- Reset tokens expire and are single-use.
- MFA is confirmed before activation.
- MFA challenge tokens cannot replace access tokens.
- Database migrations apply successfully.
- Automated tests cover the complete journey.
- Existing storage tests still pass.
- The installed production dependencies report no known vulnerabilities.

The next decision is whether to demonstrate this version locally only or prepare a controlled public test deployment for the mentor.
